# HCL Backend Starter

Reusable backend starter for a short hackathon. Current stack: Node.js, Express 5, TypeScript, pnpm, Supabase PostgreSQL, Prisma ORM 7, Zod, Helmet, and CORS.

## Current status

- Supabase PostgreSQL connection and Prisma Client generation have been tested.
- A temporary `DemoItem` model is used to practise database operations.
- Keep the starter generic until the official problem statement is known.
- Add authentication, domain models, and domain-specific routes only when needed.

## Setup

Requirements: Node.js LTS, pnpm, and a Supabase PostgreSQL project.

```powershell
pnpm install
pnpm exec prisma validate
pnpm exec prisma generate
pnpm exec tsc --noEmit
pnpm dev
```

Expected local server: `http://localhost:4000`.

Useful commands:

```powershell
# Start development server (requires the "dev" script)
pnpm dev

# Type-check without emitting files
pnpm exec tsc --noEmit

# Validate Prisma schema/configuration
pnpm exec prisma validate

# Create/apply a development migration
pnpm exec prisma migrate dev --name describe_change

# Regenerate Prisma Client after schema changes
pnpm exec prisma generate

# Inspect data in Prisma Studio
pnpm exec prisma studio

# Run the temporary database check, if src/db-check.ts exists
pnpm exec tsx src/db-check.ts
```

## Environment variables

Keep real values in `.env` only. Never commit `.env` or share database credentials with the frontend.

```env
PORT=4000
DATABASE_URL="YOUR_SUPABASE_POSTGRES_CONNECTION_STRING"
# Add these only if/when Supabase Auth is implemented:
SUPABASE_URL=""
SUPABASE_ANON_KEY=""
```

Use the database connection string provided by Supabase. Keep `.env.example` limited to placeholder values.

## Suggested structure

```text
src/
├── app.ts                 # Express middleware and route registration
├── server.ts              # Starts the HTTP server
├── db/
│   └── prisma.ts          # Shared Prisma Client instance
├── routes/                # URL/method mapping
├── controllers/           # HTTP request/response handling
├── services/              # Business logic and orchestration
├── validators/            # Zod schemas
├── middleware/            # Auth, validation, not-found, error handling
├── utils/                 # Shared helpers/errors
└── generated/prisma/      # Generated by Prisma; do not edit manually
prisma/
└── schema.prisma          # Database models
prisma7.config.ts          # Prisma CLI configuration (filename may vary by generated setup)
.env                      # Local secrets; never commit
.env.example              # Placeholder environment template
AI_CONTEXT.md             # Instructions/context for AI coding tools
```

Only create each folder/file as we add that layer; this is the target organization, not a claim that every module already exists.

## API conventions

- Use `/api/<resource>` for resource endpoints.
- Routes map URLs to controllers; controllers parse inputs and shape HTTP responses; services own business rules and Prisma operations.
- Validate request bodies, route params, and query params with Zod.
- Use `201` for successful creation, `200` for reads/updates, `204` for successful deletion, `400` for invalid input, `404` for missing resources, and `500` for unexpected errors.
- Return consistent JSON error bodies without leaking stack traces, SQL details, or secrets.
- Avoid placing database queries and business rules directly in route files.

## Hackathon working rules

1. Build only the generic foundation before the official problem is revealed.
2. Agree API contracts with the frontend teammate before implementation.
3. Use migrations for schema changes; commit `pnpm-lock.yaml`.
4. Test the main end-to-end flow early. Do not leave integration to the final hour.
5. Use synthetic data only. Never store plain-text PINs/passwords or expose server secrets.
